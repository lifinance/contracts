# Rotate Pauser Wallet (LI.FI Contracts)

The pauser may call `pause()` on `EmergencyPauseFacet`. It is a constructor immutable with no setter, so rotating it means deploying a fresh `EmergencyPauseFacet` with the new pauser and cutting it into every diamond. Repoint goes chain by chain — the coverage gap per cut is sub-second (the old facet still pauses until its selectors are replaced), so no atomic all-chain flip. Changing what the facet does is a normal `deploy-contract` change, not this skill.

## Inputs

- `--new-address` — the new pauser EOA, generated by a human. Required unless the orchestrator passes it.
- `--check` — run the Verification checks read-only and report what a rotation would change (still needs `--new-address`, which the checks compare against).
- Old pauser: read it from the live `EmergencyPauseFacet`, never from `config/global.json` (can be mid-rotation-inconsistent).

## Guardrails

- Pauser only. Never touch refund / feeCollector / withdraw (CTO-owned).
- Key generation is human. Production cuts are Safe proposals the human Ledger-signs via `multisig-rollout` → `confirm-safe-tx.ts`; hand off and wait.
- Every production repoint is a timelock-wrapped Safe proposal — no direct owner cut, no `SEND_PROPOSALS_DIRECTLY_TO_DIAMOND=true`.
- The CI pauser secret and `verifyEmergencyPauseReadiness.yml` live partly outside this repo: coordinate, never claim to have rotated a secret you can't reach.
- Exit codes when shelling out: `0` success; `1` real error (report, stop, no retry); `2` recoverable misconfig (name the missing env).

## Workflow

Order: config → repoint → sweep → funding check → CI secret. Config first because `DeployEmergencyPauseFacet.s.sol` reads `.pauserWallet` from `config/global.json` as the constructor arg — deploying earlier bakes in the old pauser. Repoint before sweeping so the new pauser is live before gas leaves the old one.

Phase 4 depends on `script/tasks/checkRotationStatusPerNetwork.ts`, which does not exist yet, so the automated funding gate stays open. Until it lands, check the new pauser's balance per chain by hand and say in the report that the funding gate was manual.

### Phase 0 — Preflight

Report, don't fix silently: `.env` present, `PRODUCTION` matches intent, `SEND_PROPOSALS_DIRECTLY_TO_DIAMOND` not `true`; `forge --version`, `gh auth status`, lifi-connect up (MongoDB, for `multisig-rollout`); new pauser confirmed with the user, old pauser read from the live facet. Check `grep -m1 "@custom:version" src/Facets/EmergencyPauseFacet.sol` and bump/confirm the version per repo convention before deploying.

### Phase 1 — Config PR

```text
/update-wallet-config --role pauser --new-address <NEW_PAUSER> --production
```

Run Phase 2 from that branch so the deploy scripts read the new pauser.

### Phase 2 — Redeploy EmergencyPauseFacet + diamondCut

Before cutting, read the pauser back from the newly deployed facet — it must be the new address.

- Staging / testnets: `/deploy-contract EmergencyPauseFacet <network...>` (deploy, verify, direct cut).
- Production EVM: `/multisig-rollout EmergencyPauseFacet` (finds every chain with the facet, one timelock-wrapped cut proposal per chain, signing hand-off, Slack).
- Tron: `multisig-rollout` does not cover it, and the Tron diamond hosts the facet too. Deploy only, via `/deploy-contract-tron EmergencyPauseFacet tron` running `deploy-core-facets.ts` — skip `register-facets-to-diamond.ts`, which cuts directly from the deployer and reverts against the timelock-owned diamond. Propose the cut through the Tron Safe + Timelock: `bunx tsx script/deploy/tron/propose-to-safe-tron.ts --to <LiFiDiamond base58> --calldata <diamondCut calldata> --timelock`. After Safe signing and timelock execution, read the facet address back from the diamond loupe.

Keep the per-network new facet addresses for verification.

### Phase 3 — Sweep the old pauser

Only after every Phase 2 cut has executed (production waits out the timelock delay) and the new pauser reads back on every target diamond, incl. Tron.

The old pauser key is `PRIVATE_KEY_PAUSER_WALLET` (`walletKeys.pauserWallet`), not `PRIVATE_KEY_PRODUCTION` (the deployer):

```text
/sweep-wallet-funds --new-address <NEW_PAUSER> --old-key-env PRIVATE_KEY_PAUSER_WALLET --production
```

### Phase 4 — CI funding check

```text
/check-rotation-status --old-address <OLD_PAUSER> --new-address <NEW_PAUSER> --role pauser --production
```

Underfunded chain → `/manage-wallet-funds send` (single chain) or `/request-dev-funds` (PR top-up) before calling it complete.

### Phase 5 — CI secret + pause-flow re-verify

Coordinate with the CI secret owner to switch the automated pause path to the new key, then confirm `verifyEmergencyPauseReadiness.yml` is green against the new pauser. Anything out of reach → explicit human follow-up.

## Verification

Complete only when:

- Every target diamond (incl. Tron) routes `EmergencyPauseFacet` selectors to the new facet, and that facet reports the new pauser (read it back; don't infer from the proposal).
- Production proposals are at `signatureCount >= 2` and posted; timelock ops execute after the delay via the scheduled pipeline.
- New pauser funded on every CI-expected chain.
- CI secret rotated and `verifyEmergencyPauseReadiness.yml` green, or the follow-up logged.
- Config PR (`pauserWallet` + `tronWallets.pauserWallet`) open; Notion follow-up noted.
- Old pauser swept to ~0 native on every chain.
